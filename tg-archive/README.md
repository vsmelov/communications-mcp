# tg-archive

Постоянный архиватор избранных Telegram-чатов поверх той же Telethon-сессии,
что у `claude_telegram_mcp`. Для чатов из `config.yaml` мы **ВСЕГДА храним на
диске живой полный дамп**: сообщения, правки, вложения, расшифровки речи — и
инкрементально пополняем его, чтобы запросы в контексте чата исполнялись
мгновенно (читаем файлы, не пейджим API).

Агенту это доступно через MCP: список всегда-архивных чатов вписан в
instructions сервера при старте и виден через тул `archive_status`; фраза
«посмотри чат с N и ответь…» должна уходить в `archive_refresh` + чтение
дампов, а не в пейджинг сообщений.

## Как это устроено

- **Формат данных** — тот же, что у `dump` в claude_telegram_mcp:
  `data/chats/<chat_id>-<slug>/dump.json + dump.md + manifest.json +
  attachments/<kind>/…`. `dump_search` MCP видит архив как обычные дампы
  (помечены `"archive": true`).
- **Realtime-события** (`sync.realtime_events`): Telegram сам пушит новые и
  правленые сообщения — строка попадает в дамп в памяти мгновенно и пишется
  на диск через `event_debounce_sec`; следом лёгкое задание докачивает медиа
  и транскрипт вне очереди плановых. Удаления тоже ловятся (пометка
  `✖️ (удалено)` — сообщение остаётся в архиве). Плановый проход при этом
  остаётся как сверка: событие, дропнутое Telethon'ом из-за «яда» (см.
  ниже), доедет им.
- **Один воркер, всё последовательно.** Аккаунт один, лимиты Telegram общие,
  поэтому никакой параллельности: паузы между запросами истории
  (`history_wait_sec`), между скачиваниями вложений (`media.delay_sec`),
  между чатами (`between_jobs_sec`), плюс джиттер ±25%.
- **FloodWait** до часа Telethon пересыпает сам (`flood_sleep_threshold`);
  более длинный — сервис запоминает срок и не трогает API до его истечения.
- **Бэкфилл** идёт кусками по `backfill_batch` сообщений за проход, пока не
  дойдёт до начала истории (`backfill_done` в manifest). Новые сообщения
  подтягиваются каждый проход, последние `edit_window` сообщений
  перечитываются (ловим правки).
- **Вложения:** максимум 10 МБ (`media.max_mb`), не больше `per_cycle` штук
  за проход. **Видеокружки** — скачивается исходник (до 100 МБ), ffmpeg
  извлекает аудиодорожку (`<id>_audio.m4a`), видео удаляется; если аудио
  больше 10 МБ — не храним вовсе.
- **Транскрибация** (`transcribe` в config.yaml). В `dump.md` текст помечен
  `[speech]`, в `dump.json` — поле `transcript`. Два провайдера:
  - `provider: telegram` (по умолчанию) — **бесплатно**, силами самого
    Telegram Premium (`messages.transcribeAudio`, тот же механизм, что у
    telegram-transcribe-service; его готовые расшифровки Telegram отдаёт из
    кэша мгновенно). Файл не нужен — работает по (peer, msg_id), поэтому
    расшифровываются даже кружки >10 МБ, которые мы не храним. Умеет только
    voice и video_notes.
  - `provider: openai` — платно через OpenAI STT (`model`, $0.003/мин у
    mini), умеет ещё и audio-файлы. Каждый файл — строка в
    `data/transcribe_ledger.jsonl`; в `/status` и на дашборде — траты
    всего / за сутки / за час, дневной стоп-кран `daily_budget_usd` (деф.
    $5). Ключ — OPENAI_API_KEY из `../.env` (env_file compose).
- Удаления сообщений не детектим: в личках id сквозные по всем чатам
  аккаунта, дыры в нумерации ничего не значат.
- **«Ядовитые» сообщения (TypeNotFoundError).** Telegram иногда отдаёт
  TL-конструкторы новее, чем слой установленного Telethon (замечено на
  пере-сериализованных webpage-превью ссылок; конструктор `3ae56482` при
  Telethon 1.44). Такое сообщение валит разбор целой страницы истории.
  Архиватор это переживает: страница перечитывается бисекцией
  (`_careful_range`), непарсящиеся сообщения пропускаются и считаются в логе
  и `manifest.archive.unparseable_total`. Приём realtime-обновлений отключён
  (`receive_updates=False`) — тот же яд в GetDifference раньше рвал
  соединение. Когда выйдет Telethon с новым слоем — просто пересобрать образ.

## Мониторинг: http://127.0.0.1:8722/

Встроенный дашборд (та же aiohttp, отдельный сервис не нужен). Показывает по
каждому чату: сообщений, покрытие, статус бэкфилла, очередь медиа и
расшифровок, время последнего синка; общий статус (очередь, FloodWait,
последняя ошибка) и траты на транскрибацию: всего / за сутки / за час,
прогресс дневного бюджета, последние расшифровки из журнала.
Автообновление каждые 10 секунд.

## HTTP API (127.0.0.1:8722)

- `GET /` — HTML-дашборд мониторинга (см. выше)
- `GET /health` — живой ли сервис
- `GET /status` — состояние всех чатов (покрытие, бэкфилл, очередь, FloodWait)
- `GET /ledger?limit=25` — последние записи журнала транскрибации (USD)
- `POST /refresh` `{"chat": "<id|@username|часть названия>", "timeout_sec": 120}` —
  чат встаёт в начало очереди, ответ приходит после синка. Это «оперативно
  докачать перед ответом» — MCP-тул `archive_refresh` зовёт именно её.

## Интеграция с claude_telegram_mcp

В `server.py` добавлены тулы `archive_status` / `archive_refresh`
(конфиг — `TELEGRAM_ARCHIVE_URL`, `TELEGRAM_ARCHIVE_ROOT` в `.env` MCP).
Сценарий для модели: `archive_refresh(chat)` → Read/Grep `dump.md`.

## Запуск

```bash
docker compose up -d --build
```

`restart: unless-stopped` — контейнер стартует сам вместе с Docker Desktop
(проверь, что в Docker Desktop включён автозапуск при логине). Остановленный
руками (`docker compose stop`) контейнер сам не оживёт — это осознанно.

Сессия: `data/session/archiver.session` — копия `mcp.session` из
claude_telegram_mcp (общая авторизация; копия не плодит устройств).
Прокси из контейнера: `http://host.docker.internal:10801` (см. `.env`).

Запуск на хосте (для отладки; не одновременно с контейнером — лимиты общие):

```bash
TELEGRAM_PROXY=http://127.0.0.1:10801 python -m archiver.main
```

## Добавить чат в архив

Дописать в `config.yaml` в `chats` строку `- query: "<id или @username>"` и
`docker compose restart tg-archive`. История дольётся бэкфиллом сама.
